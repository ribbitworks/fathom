# Fathom — Issues

**Status:** Working list
**Last updated:** 2026-11-07

Known problems and deferred work that are not yet scheduled in the [Implementation Plan](design/implementation-plan.md). Each item says why it was deferred. When an item is scheduled or resolved, it moves to the document that owns it, or is removed.

## Access History

- **Sign-ins, sign-outs, and failed sign-ins:** Not recorded in the access history. The server's request log already records each sign-in attempt with its time and network address, and active sessions are kept in the database. Deferred by the owner; worth revisiting if HR or IT asks for them.
- **One name for Restricted and Confidential views:** The server's `includedRestricted` flags, on the org chart, People and the hiring plan, are also set when Confidential details are shown, and are recorded as `restricted-viewed`, so the names say less than they do. Found in review on 2026-11-07.

## Roles

- **Access limited to one's own part of the organization:** Permissions apply to everyone's data, so Engineering Managers see Restricted details for everyone, and a Project Manager cannot be limited to editing their own projects. The owner decided on 2026-11-04 that permissions will take a scope, such as one's own reporting line, and that it must be built; it waits until roles are editable and Teams and Reporting Lines is built, and may use the linked person records proposed in [Roles](product/roles.md#access-to-your-own-record-and-your-reports).
- **A second person confirming Confidential grants:** A change granting Confidential data, to a role or to an account's role, takes effect at once, without a second person confirming it. It is recorded in the access history and marked there as worth checking, as is every account created. Deferred by the owner on 2026-11-05, since few applications have such a check; built if HR asks for it.
- **Unusual permission sets offer what the server refuses:** Some permissions need another that the Roles page does not name, so a role holding one without the other is shown actions the server then refuses. No starting role is affected. Edit Configuration cannot make or change a list without View People, yet the Lists page offers **New list** and **Edit**. Edit Configuration with View People, but not Edit People, is offered **Delete column** for a live column, which the server refuses. Edit People says it changes reporting lines, but changing a manager needs Edit Restricted details too, since reporting lines' dates are Restricted, and the People grid still lets the manager be changed. Feature team permissions need both View People and View Org chart, while the Roles page can name only one permission a permission does nothing without. Found by the permissions tests on 2026-11-05.

- **Refusals shown in general words:** The web shows every refusal for lack of permission as "You do not have permission to do this. Your role may have changed.", so a refusal the server words for the user, such as that adding people needs seeing positions, or that an Approver who sees a draft's details must decide it, never reaches the screen. Found while letting the built-in lists' visibility change, on 2026-11-05.
- **One tier for each recorded change:** A change, a rejection, and a cleared rejection each record one tier, the most sensitive of the fields they cover, while each tier is a permission of its own, so a role that sees Confidential but not Restricted data could see a rejection reason recorded at Confidential for a draft that also changed a Restricted detail. Fathom's starting roles that see Confidential data also see Restricted data, so none is affected today. Found on 2026-11-05.

## Planning

- **Cycles from the 29th to the 31st:** A monthly cycle that starts on one of these days starts on the last day of shorter months. Changing one such cycle's length counts the cycles after it from that cycle's own start, so they can stay on the 28th from then on. Deferred by the owner on 2026-11-05 as rare in practice.
- **Freezes between cycles:** A stream's cycles follow one another with no gap, so a freeze, such as the end of December, can only be a short cycle with a name and number of its own. Deferred by the owner on 2026-11-04 until a stream needs one; a cycle marked as a gap, unnamed and not counted, would fit the cycle patterns.
- **Undoing changes to the plan's records:** The change history refuses undoing a change to a release stream, cycle pattern, or release, since undoing one can break the rules for cycles and releases that approving checks. Deferred until undo is wanted for them.
- **Ordering release streams:** Streams keep the order they were added in; moving them, as the Decisions Log allows, is not built yet. Deferred until an organization has enough streams for the order to matter, since the monthly resource grid's picker defaults to the first.
- **Which delivery a feature is needed by:** The release warning checks each needed feature against its project's earliest customer delivery date still to come, so a phased project warns about features only its later deliveries need. Saying which delivery each feature is needed by was deferred by the owner on 2026-11-03 until the warnings prove noisy.

## Account Administration

- **Two administrators choosing the same email address at once:** Two accounts given the same email address at the same moment, by creating or changing them, can give a server error instead of the "already exists" message. Accepted by the owner as unlikely with 20 to 30 users.
- **Changing a password after deactivation:** Changing one's own password goes straight to Better Auth, which does not check that the account is still active, so a session made just before an account is deactivated could still change its password. The session cannot be used for anything else. Found in review on 2026-11-03.
- **Two users taking the same name at once:** The check that a name is free when users change their own takes no lock, so two users renaming themselves to the same name at the same moment could both succeed, and Administrators creating or renaming accounts do not check names at all. Both renames are still recorded and marked as worth checking. Accepted as unlikely with 20 to 30 users, like the email address case above. Found in review on 2026-11-03.

## Lists

- **Sorting, filtering, and saving views of lists:** The Lists table cannot be sorted or filtered by its columns, such as to lists with or without choices, or saved as views, as People can; only its search, the All, Built in, and Custom switch, and Show retired narrow it. The switch stays once column filters come. Asked for by the owner on 2026-11-06, to follow planned hires as rows of People.
- **Splitting the lists module:** `apps/server/src/data/lists.ts` holds both reading lists with their drafts and drafting changes to them, and is large enough to split. Deferred by the owner on 2026-11-01 as low risk at Fathom's size.
- **Reading drafts' history:** Reading lists or people reads each draft's whole history of changes, to name who changed it, and undoing changes to drafts of lists reads every list again for each record undone. Both are fast at Fathom's size; deferred by the owner on 2026-11-01 until tables grow.
- **Undoing a list's creation:** Undoing a change set that created a live list deletes the list without checking that nothing draws on it, so undoing an old change set that created what is now the built-in Positions list, in a database with no people, would remove it. Such change sets predate drafts, so few databases hold one; found by review on 2026-11-04, older than the built-in lists.

## Drafts

- **A draft's lineage:** No one place shows how a draft came to be where it is: who made and changed it, who rejected it and why, when it was sent again, and which drafts it uses or that use it. The record's menu, the Drafts page and the change history each hold part of it, which makes a draft waiting on a rejected one hard to follow. A view of a draft's lineage was suggested by the owner while testing drafts by hand on 2026-11-02.
- **Unnamed in the access history:** The access history names each person by their live record, so a Restricted change to someone only drafted to be added shows them without a name until their draft is approved.
- **An order draft that moves only Restricted columns:** A draft of the column order that moves only columns a reader may not see, such as Start or Manager since, is still sent to that reader as a draft of the order whose live and drafted orders are the same. Found in review on 2026-11-04.
- **A reason's tier in the change history:** A rejection's reason is recorded with the tier of its draft when rejected, so, unlike the draft's values, it does not become more sensitive in the change history if a column's list later does.
- **Publishing drafts after losing a permission:** Publishing your unpublished drafts checks only that you may make some kind of draft, not each draft's own permission, so someone whose role no longer lets them change planned hires, people, or configuration can still send drafts they made earlier for approval. Found in review on 2026-11-05, and deferred by the owner as an edge case.
- **A draft's changer counted after it ends unapproved:** whoever changed a draft counts as its changer until the record's draft is approved or discarded. A draft can also end without either, such as one published back to the live value, approved with no change left, or an emptied order. Then someone who changed it earlier still counts as having changed the record's next draft, so another approver must approve it. This errs on the safe side. Found in review on 2026-11-07, while building no self-approval.

## Dependencies

- **Advisories in minimatch and glob:** Two medium advisories, published by 2026-10-30, affect minimatch before 11.0.1 (denial of service from crafted patterns) and glob 9 to 14.0.1 (a cancelled search can keep reading files). They reach the server through @fastify/static, and development tools such as ESLint, markdownlint, and Testcontainers. In Fathom, the patterns come from code, never from users. The fixed versions are new major versions that the packages depending on them do not accept yet, so they wait for those packages' updates. Both fixes were released on 2026-10-27, so the Security Plan's 180 days for medium findings runs to 2027-04-25.

## Releases

- **One image name built two ways would be scanned once:** The security report and the daily image scan scan each image name once, after building every Compose file, so if two Compose files built the same name with different settings, only the last build would be scanned. Today the development and production Compose files build the database image from the same Dockerfile and settings. Checking that they still match before scanning is deferred by the owner on 2026-11-07. Found in review on 2026-11-07.
- **Workflow scans kept 90 days, not a year:** The Publish release images and Scan images daily workflows keep each scan and its summary with the run for 90 days, the longest GitHub allows a public repository's artifacts, while the [Security Plan](security/security-plan.md#enforcing-the-plan) keeps scan results for at least a year. Until the location agreed with IT takes them, a scan older than 90 days is kept only where it was run by hand. Found in review on 2026-11-07.
- **Images are not repeatable byte for byte:** Building one release tag twice gives images with the same labels and dates but different digests, since each build applies the security fixes released by that day, and installed files keep the times they were built. Writing every file's time from the commit (BuildKit's `rewrite-timestamp`) did not make two builds of the proxy image match on 2026-11-07. Until images are repeatable, a running image is matched to its source by its labels rather than by rebuilding it. Found in review on 2026-11-07.
