# Fathom — Visual Design

**Status:** Agreed with the owner
**Last updated:** 2026-11-04

How Fathom's screens look and behave, so every page is built the same way. It applies the components and typeface chosen in [ADR 0004](../adr/0004-ui-components.md). The theme in `apps/web/src/theme.ts` holds the values; this document holds the rules.

## Principles

The owner's principles come first:

- **No instructional text:** If a screen needs explaining, the design is wrong. No hints, help lines, or placeholder sentences telling people what to do. Labels are one or two words, and an optional field may add "(optional)" to its label. Familiar patterns, such as a grip handle for dragging, speak for themselves. Saying what an action will do, as a confirmation does, is not instruction, and neither is reference material, such as what each role lets a user do.
- **No assumptions:** Screens add no purposes, defaults, restrictions, or wording the owner has not asked for. Where something is unclear, it is left out and the owner is asked.
- **Keyboard-first data entry:** Wherever people enter or change data, everything can be done from the keyboard, and adding many items in a row never needs the mouse: Tab moves between fields, Enter saves and starts the next item, Esc cancels, and arrow keys move between items. Where many records are entered, such as resources, editing works like a spreadsheet, including pasting rows.
- **The bar:** Top-tier modern products, such as Linear or Notion: calm, dense, and obvious.

The rest follow from them:

- **Quiet and dense:** Fathom is a work tool used every day, so pages favour clear structure and plenty of information over decoration. As few borders, lines, labels, and columns as the task allows; metadata, such as who changed something, stays out of the way.
- **One main action per screen:** Every other action is secondary or in a menu.
- **Controls when needed:** Controls that are not always needed, such as grip handles for dragging, appear on hover or keyboard focus. A row's "⋯" menu button is always shown, so its actions are easy to find.
- **No wasted space:** Layout serves the content; nothing takes width or height it does not earn.
- **Colour means something:** Neutrals carry the page. Sea blue marks actions and the current place. Other colours appear only for meaning, such as green for active, yellow for changes worth checking, and red for problems.
- **Never colour alone:** Anything shown by colour is also shown in words, visible or read aloud by screen readers.
- **Both modes:** Light and dark modes follow each person's system setting.
- **International:** Names and text in any language and script are shown, entered, searched, and sorted as well as English is: no screen assumes Latin letters, a given name first, or one name per person, and text is never cut so a character breaks. Search ignores letter case and accents, such as é or ё, but not marks that make another letter in other scripts, such as Japanese が, though Cyrillic letters such as й also match their plain letter. Sorting, dates, and counts follow each person's own language settings, and scripts the typeface lacks fall back to the system's fonts. The [seed data](development-setup.md#fictional-seed-data) includes names in other scripts, so every screen is tried with them.

## Layout

- **Frame:** A deep-water sidebar on the left, the same in both modes, groups pages into sections. The sidebar shows only the pages the user's roles allow, including pages still to come, marked "Later", so people can see what Fathom will offer them. Fathom opens on the Overview, or, for a user who may not see the plan, on the first page their roles allow, or Help's Roles page if there is none. Help is the last section, open to everyone, with its own icon for each page. A top bar names where the user is and holds their account menu, wide enough for their email address, with Change name, Change password, and Sign out.
- **Collapsed sidebar:** The sidebar collapses to a rail of icons, each naming its page on hover or focus, and remembers the choice.
- **Narrow screens:** The sidebar opens from a menu button, and closes when the user moves to another page.
- **Pages:** Each page starts with a heading and the page's main action on the right. Content sits in bordered panels on a canvas a shade darker than them.
- **History pages:** Change history and Access history, in the sidebar's History section, look alike: a search field, like a table's, then one row for each entry, newest first, with its date, year, and time, naming who did what in a sentence, with details dimmed after a colon, and a yellow dot, read aloud as "Worth checking", before entries that deserve a second look. The change history has a sentence for each record a save changed, such as "changed the list Sites: Name from Sites to Locations", where the field is in semibold and each value is set apart on a light ground, as a value is in code, as wherever a change is described, in a record's menu or on the Drafts page; records of a kind added or deleted together share one, such as "added 150 people", naming ten, with Show all for the rest. A save that changed several records lists five, with Show more for the rest. Show more at the end of the page reads older entries. The change history's search looks on the server in who made each change and the names and values involved, reading back through up to 2,000 saves at a time, with Show more to read on, and shows what matches first in each entry; the access history's searches the latest entries it shows.
- **Roles help:** Help's Roles page names each role beside what it lets a user do, with a sea-blue check, read aloud as "Your role", before the user's own roles, followed by what each sensitivity covers. Wherever roles are chosen, each role shows the same description under its name.
- **About Fathom:** The last item in Help, open to everyone, opens a box in the middle of the screen, over the current page, rather than going to another, unlike dialogs, which open near the top, since it asks nothing of the user, with Fathom's mark and name above three rows: Version, such as 0.3.0, or 0.3.0, plus 4 commits, or Unreleased, as [Decisions Log](../product/decisions.md#platform-and-operations) sets out; Commit, the short commit, followed by "modified" for a build from files that differ from it; and Committed, the commit's date, such as November 2, 2026. A build given nothing from git, as [Development Setup](development-setup.md#ways-to-run-fathom) describes, shows each as Unknown.
- **Drafts help:** Help's Drafts page names each mark a person, list, or choice with a draft can show, drawn as on the People table and the Lists page, beside what it means, followed by what happens to a draft once saved, approved, rejected, or discarded, and what each choice in the Draft menu shows.
- **Accounts:** Each row ends with an Edit button, the account's one action, opening a dialog that changes its name, email address, and roles, with Reset password and Deactivate, or Reactivate, as quiet text buttons on the left of its foot, Deactivate in red, each asking to confirm. The user's own row has a sea-blue "You" badge beside their name, lighter in dark mode, and offers no password reset. Controls for changes the server would refuse are turned off, such as the Administrator role and Deactivate for the last active Administrator.
- **Sign-in and problem pages:** Only Fathom's name and mark above the form or message, with no other words.

## Type and Colour

- **Typeface:** IBM Plex Sans, at weights 400 for text, 500 for emphasis, and 600 for headings and names. Weight 700 is bundled for Mantine's own bold text, such as table headings.
- **Figures:** Dates, times, and numbers that line up in columns use figures of equal width.
- **Colours:** Defined once in the theme as CSS variables and used by name, never written into a page.

## Components

- **Tables:** Lists of records are tables in a panel, using the full width, each text cell on one line and cut short when it does not fit. Every table's column headers look alike: small, semibold, and dimmed, on one line of a set height, and its header row stays in view while its rows scroll. A page of a long table, such as People or Accounts, fills the window, and the table scrolls within it. A row's actions are in a menu behind a "⋯" button at its end, always shown, except on Accounts, where an Edit button holds them all. What a table's rows hold sets how tall they are: People's are dense for editing, and Accounts' show each person's initials, name, and email address. Rows show no audit detail, such as who changed a record or when; any date shown includes its year.
- **Side panels:** Every side panel, such as a record's or the Metrics panel, sits beside the content, which narrows to make room and stays usable. Dragging the edge between them, or moving it with the arrow keys once focused, resizes the panel, leaving the content room, and each kind of panel keeps its width for next time, starting at 640 pixels. On a narrow screen a panel covers the screen and keeps focus until it is closed. Clicking a row opens its record in a panel at its own address; Esc, the close button, or a click on the page outside the panel, the rows, and the controls closes it.
- **Entering data:** Where items are added or changed in a list, they are edited in place, from the keyboard: an empty row at the end takes new items, Tab moves between fields, Enter saves and starts the next, Esc cancels, and arrow keys move between items. Pasting several lines adds one item for each. Problems show on the row being edited.
- **Editing like a spreadsheet:** Tables where many records are entered, such as People, work like a spreadsheet. Arrow keys, Home, End, and Tab move between cells, Tab on to the next row at the end of one, and Ctrl+Home and Ctrl+End go to the first and last cells; Enter, F2, or typing edits a cell; Enter saves and moves down, Tab saves and moves across, Esc cancels, and Delete clears. A column whose values follow from another's, such as Team, which follows from Manager, is read only, and pasting into it is ignored. Empty rows at the end take new records, which the page's main action, such as New person, goes to: Tab goes straight on to typing in the next cell, and Enter adds the record. A row being filled in is tinted as the draft it will be and marked "New, not saved yet" after an open dot, naming in red what is wrong so far, such as "Someone already has that Employee ID", or otherwise, in grey, any required column still empty, such as "Site needed". Its menu, also opened with Shift+F10, offers Clear row, which takes the row and what it holds away. A value that is wrong shows in red in its cell, and a value refused when saved keeps its editor open with a red border; the problem is named in red under the row, in its first cell. Where the cell puts its old value back instead, as when Delete or leaving the cell is refused, the row is as it was and names nothing. An added record shows at once, as a draft adding it, and cannot be changed until it is saved. Pasting rows copied from a spreadsheet adds one record for each. A column drawing on a list is edited by typing to narrow its choices, which drop down below the cell, and picking one. A web link column shows each link's text, or the host of its address when it has none, such as example.com, underlined as a link that opens in a new tab, with the address shown on hover; the person's menu offers opening each link from the keyboard. Editing a link opens a small form below the cell with the address, checked once it is left, and the text to show; Tab moves between the two, then on to the next cell, and clicking away saves. Pasting into a web link column takes each cell's text as the address. A web link column is searched and filtered by its links' text and addresses, and sorted A to Z by the text shown. A checkbox column, such as Manager?, shows a checkbox in each cell, checked or empty, in the light green Live row under a draft too; one click, Space, or Enter checks or unchecks it, and typing does nothing. Pasting Yes, Y, X, True, or 1 into it checks it, and No, N, False, 0, or nothing leaves it empty. A checkbox column is filtered by Yes and No, which the metrics count too, and sorted checked first or unchecked first. Each column is as wide as what it can hold, up to about 30 characters: a column drawing on a list fits its longest choice, so a cell holding several is cut short, a date column fits the longest date, and a text or web link column the longest value it held when the page opened. The first column has room for a draft's mark. No width follows what is typed, so editing never moves the table. Every column can be dragged by its header, or moved with Alt and the arrow keys or from its menu.
- **Searching, filtering, and sorting:** A search field above a table finds rows with every word typed anywhere in them, ignoring letter case and accents; Cmd+F on a Mac, or Ctrl+F elsewhere, goes to it from anywhere but a dialog, and Esc clears it, then goes back to the table. Each column's menu, open to viewers too, sorts by it, A to Z, by date, or in its list's order, adding it as the next level of the sort, or changing its direction in place when it is sorted already. It also opens the column's filter beside the header: text a value contains, dates from and to, typed as 2026-10-31, or choices to show, with retired ones under their own heading, each with an option for empty values. Sorted and filtered columns are marked in their headers. Above the table, each level of the sort is named in a pill, such as "Level ↑", in order, and so is each filter, each pill removing what it names, beside how many rows there are, such as "150 people", or, while rows are hidden, how many are shown, such as "35 of 150", with Clear all, which also clears the sort. Rows keep their place while they are edited, until the view next changes, and when nothing matches, the table says so.
- **Saved views:** A Views menu after the search field lists the table's saved views by name, the applied one checked, and applies the one chosen. It is named after the saved view applied, with a dot once the view has changed since, or, with none applied, once it differs from the table's default view, and offers Clear view, like Clear all but closing the metrics too, Save view…, which asks for a name in a dialog listing under Includes each part the view keeps, one a line, such as Sort: Level ↑, Draft: Drafts applied, and Metrics: Position by Site, and, for views the user may change, Update with the view as it is now, Rename…, and Delete view, which offers Undo. It is left out while there are no saved views and nothing to save.
- **Metrics:** A Metrics button after the Draft menu, and Break down by in each column's menu, open the Metrics panel beside the table, a side panel as [Side panels](#components) sets out. The panel says how many rows it counts, such as "35 people", or with drafts beside live "35 people with drafts, 34 live", and offers Break down by and, once a column is chosen, and by, listing only the columns the table shows, without required text such as names. One column shows a row for each choice, in its list's order, retired ones only when someone holds them, then Empty when anyone is, each with its count and share; a column without choices shows Populated and Empty. Two columns crossed show a table with an All row and column, as counts or as shares of everyone counted, picked with Count and Share. With drafts beside live, a figure whose live figure differs has it under it, dimmed and marked Live. Where someone may hold several choices, a note says the figures can add up to more than their total. The metrics are part of the view, kept in saved views, once a column is chosen; an open panel with no column chosen is nothing to save. Esc or the close button closes the panel and puts focus back on the Metrics button. Clear all leaves it open; Clear view, which clears the whole view, closes it.
- **Ordering:** Where people set an order, rows have a grip for dragging on wide screens, shown on hover or focus, and Alt with the arrow keys moves the selected row. Each row's menu offers the same moves and shows each action's shortcut.
- **Retiring:** Records that others use are [retired](../product/domain.md#table-terms) rather than deleted. Retired records are shown only when asked for.
- **Monthly resource grid:** The grid in the [Decisions Log](../product/decisions.md#planning) keeps people's names fixed on the left while months scroll sideways. Cycle ends are thin vertical lines labelled with their names, and each release a line on its Ships on day, for the release stream chosen in a picker after the search, kept in the page address and saved views. Each cell lists that month's work, each feature with its percentage, and the month's total, marked when over- or under-allocated as the Decisions Log sets out. For readers who see Restricted data, months outside a person's employment are shaded and allocations left there by a date change are marked with their warning. A Warnings filter shows only the rows that have any. Allocating, from a cell or a row's menu, picks a feature, a percentage, and a from month and optional to month. Rows can be grouped by manager, by feature team, or not at all, each group with a total row of the person-months allocated against those available, and the whole organization's total at the foot. Drafts are shown in cells as on tables.
- **Releases timeline:** Below the table of release streams, the timeline the [Decisions Log](../product/decisions.md#planning) sets out. Unlike the roadmap and timeline board below, from [ADR 0009](../adr/0009-roadmap-and-timeline-views.md), whose columns are cycles and whose cards are features, its axis is time itself, each day the same width, so cycles are drawn at their real lengths and streams with cycles of different lengths line up.
  - **Layout:** Stream names stay on the left while the timeline scrolls sideways. Each stream has a lane of cycles above a lane of releases, each release a span across its cycles with a diamond on its Ships on day, joined to the end of its last cycle by a dashed line when it ships on another day. A release with a draft has a dashed edge. A red line marks today, the reader's own date rather than the date in UTC, labelled in a row of its own above the axis. A name that does not fit its cycle or release is left out rather than cut short, and hovering names every cycle and release with its dates.
  - **Zoom:** All, Year, 6 months, Quarter, Month, Week and Days show the whole timeline, three years, two years, a year, six months, six weeks or two weeks across the view, never less than the view's width, and − and + show half as much again, or a third less, from two weeks to the whole timeline. The zoom is kept for next time, starting at Year.
  - **Axis:** Two rows of dates. Year, 6 months and Quarter name their own period above the next smaller one: years over half years, such as Jan to Jun 27; half years over quarters, such as Q1 27; and quarters, such as Q1 2027, over months. Month and Week name months over weeks, each named by its Monday, with the days as short marks along the bottom wherever they are far enough apart to see, and Days names months over days, such as Mon 9. All, and zooming with − and +, cut it as finely as its names fit. A name too long for its period is shortened, such as to Jan or Q1, or left out.
  - **Scrolling:** The timeline opens with today a sixth of the way across, and Today goes back there. Changing the zoom or the window's width keeps today there, or, once the reader has scrolled, the day in the middle of the view.
- **Roadmap and timeline:** **Proposal:** the board below, from [ADR 0009](../adr/0009-roadmap-and-timeline-views.md), is not yet agreed and will be revised with the owner.
  - **Layout:** The roadmap is a board with a column for each cycle, under its release's name, and Later at the end, and features as cards showing their name, status, and feature team. The timeline is the same board with a row for each feature team, and a last row for features with none. Within a row, each feature has its own lane: its card sits in its target cycle, where the feature ships, at the end of a bar spanning the months its allocations cover, which may reach back across earlier cycles. Each cycle's column can show its estimated demand against the capacity available, and Later the demand of features that target no cycle. The board shows one release stream at a time, the first in their order by default, with a picker kept in the page address and saved views.
  - **Moving:** A card is dragged to another cycle, or on the timeline to another row, or moved with Alt and the arrow keys, left and right to the next cycle and up and down to the next row, or from Move to cycle… and Move to feature team… in its menu. Moving it changes its target cycle or feature team in its draft; moving it back to its live place takes that change out of the draft, and the draft away once nothing else in it differs.
  - **Drafts:** A moved card is tinted and marked Draft, Unpublished, Rejected, or Being changed, as drafts are on tables, and its live place keeps a dimmed copy marked Live, as a moved choice does. A card someone else is changing cannot be moved. The Draft menu works as on tables: Live only shows the board read only, without dragging, as it is for those who only view. A cycle's demand that a draft changes has its live figure under it, dimmed and marked Live, as in Metrics.
  - **Approving:** Approvers approve or reject a move from the card's menu, the Draft menu, or the Drafts page, which describes it as a change to the feature's target cycle or feature team.
- **Dialogs:** Creating and changing settings, such as a list's name, happens in dialogs, which cannot be closed while a change is being saved.
- **Drafts:** How drafts look, and what can be done with them, on every table that has them.
  - **Marks:** A record with a draft is tinted light blue and marked after a dot: Draft, Draft: added, Draft: removed, Draft: moved, Draft: reordered, Draft: retired, or Draft: restored, with a yellow dot, or Rejected, with a red one. The user's own unpublished draft has the same mark with a hollow yellow dot, read aloud as unpublished. A rejected draft that is unpublished, and an unpublished draft with no other mark, such as on the Drafts page, are marked Unpublished, after a hollow yellow dot, and a record someone else has unpublished changes to is marked Being changed, after a grey dot, read aloud with who. A record a draft removes is struck through and cannot be changed. Each tint has a darker version in the dark scheme, so text on it stays readable. A warning about a value is marked after a red dot in its cell, such as Left after a manager whose end date has passed, read aloud with why.
  - **Rows:** On People, each cell a draft changes is yellow, or soft red once rejected. Under the draft row is the person's live row, light green, dimmed, and marked Live: read only, skipped when moving between cells, and with each changed cell's live value read aloud.
  - **Columns:** A column with a draft is marked under its name, so the mark does not widen it, and a changed column has its live copy beside it, marked Live. A new column order shows the columns in their new places, each moved column marked Draft: moved, unless it is removed.
  - **Lists:** A list's row is marked Draft while anything in it waits, Draft: reordered when only its order does, and Rejected only once everything drafted in it was rejected. A choice drafted to be removed is struck through in the row and not counted. In the panel, each choice with a draft is tinted and marked, with its live row under it, and a moved choice is marked Draft: moved, with its old place dimmed and marked Live. A list or choice drafted to be retired or restored stays where it is until approved. The rows are not a spreadsheet's, so no single cell is tinted.
  - **Menus:** A record's menu starts with its name, then a divider. Its draft section starts with the draft's mark and any rejection's reason, then one line for each change, naming the field in semibold and setting each value apart, as in code, with who made the change. A list's menu has a short section for its own draft and one for a new order of its choices, each with its mark, who made it, and any reason. A click anywhere in a menu but its items closes it.
  - **Publishing:** While the user has unpublished changes, the top bar, beside their account, shows Publish with how many, such as Publish 3 changes, which publishes them all at once, and a menu listing them, with Discard all…, which asks first. A record someone else is changing is read only, and its menu says Being changed by, with who, and that it can be changed once they publish or discard their changes; Approvers cannot decide it, nor the user's own unpublished draft, whose menu says only they see it until they publish it.
  - **Actions:** Those who may edit discard a draft, or resubmit a rejected one; a new order is discarded with Discard new order. Approvers approve or reject a waiting draft from its menu. A rejected draft offers Approvers nothing to decide until it is resubmitted, and a draft that depends on a rejected draft has Approve disabled, with "Waiting for a rejected draft to be resubmitted" under it. A moved column whose own draft waits, while the new order also waits, has one Approve… and one Reject… that decide both, and the dialog names both.
  - **Deciding several:** The Draft menu offers Approve N drafts… and Reject N drafts… for the waiting drafts shown, under a Waiting drafts label that, when a search, a filter, or Drafts applied hides some, says how many are shown, such as 9 of 11 waiting drafts shown. The dialog says how many related drafts it includes, and how many drafts it skips because they depend on a rejected draft.
  - **Draft menu:** The Draft button above the table, marked while its choices are not the defaults, filters to records whose drafts are waiting or rejected, or that have no draft, shown in a pill such as "Draft: Waiting", and chooses what to show: Drafts beside live, the default; Drafts applied, everything as it will be once the waiting drafts are approved, without live rows or removed records, and with rejected drafts taken back, so the Rejected filter is unavailable; and Live only, everything as it is now, read only, with the filter unavailable. Both choices are kept in the page address and in saved views.
  - **Drafts page:** Every draft as a sentence with what it changes, with a search. Approvers select waiting drafts there to approve or reject; a rejected draft, or one that depends on it, cannot be selected.
- **Undo, not confirmation:** Changes save at once, without asking for confirmation, except approving and rejecting drafts, which cannot be undone and so ask first, and the latest can be undone with Cmd+Z or Ctrl+Z. Changes seen in place, such as an added or moved item, show no notification. Changes that take something out of view, such as retiring or removing it, show a notification at the top right offering Undo, which closes after a few seconds or when a newer change is made. Failures stay until closed.
- **Empty and failed states:** An empty table says so in a few words. A table that cannot be loaded says so and offers Try again.
- **Messages:** Problems are shown in plain words saying what to do next, never as raw errors.
- **Styles:** Mantine's components, theme, and style props, such as a one-off size or margin, come first. Anything more goes in a CSS Module, never in a `style` attribute.
