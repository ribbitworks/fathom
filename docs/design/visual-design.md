# Fathom — Visual Design

**Status:** Agreed with the owner
**Last updated:** 2026-11-01

How Fathom's screens look and behave, so every page is built the same way. It applies the components and typeface chosen in [ADR 0004](../adr/0004-ui-components.md). The theme in `apps/web/src/theme.ts` holds the values; this document holds the rules.

## Principles

The owner's principles come first:

- **No instructional text:** If a screen needs explaining, the design is wrong. No hints, help lines, or placeholder sentences telling people what to do. Labels are one or two words, and an optional field may add "(optional)" to its label. Familiar patterns, such as a grip handle for dragging, speak for themselves. Saying what an action will do, as a confirmation does, is not instruction, and neither is reference material, such as what each role lets a user do.
- **No assumptions:** Screens add no purposes, defaults, restrictions, or wording the owner has not asked for. Where something is unclear, it is left out and the owner is asked.
- **Keyboard-first data entry:** Wherever people enter or change data, everything can be done from the keyboard, and adding many items in a row never needs the mouse: Tab moves between fields, Enter saves and starts the next item, Esc cancels, and arrow keys move between items. Where many records are entered, such as resources, editing works like a spreadsheet, including pasting rows.
- **The bar:** Top-tier modern products, such as Linear or Notion: calm, dense, and obvious.

The rest follow from them:

- **Quiet and dense:** Fathom is a work tool used every day, so pages favour clear structure and plenty of information over decoration. As few borders, lines, labels, and columns as the task allows; metadata, such as who changed something, stays out of the way.
- **One main action per screen:** Every other action is secondary or in a menu.
- **Controls when needed:** Controls that are not always needed, such as grip handles for dragging, appear on hover or keyboard focus. A row's "⋯" menu button is always shown, so its actions are easy to find.
- **No wasted space:** Layout serves the content; nothing takes width or height it does not earn.
- **Colour means something:** Neutrals carry the page. Sea blue marks actions and the current place. Other colours appear only for meaning, such as green for active, yellow for changes worth checking, and red for problems.
- **Never colour alone:** Anything shown by colour is also shown in words, visible or read aloud by screen readers.
- **Both modes:** Light and dark modes follow each person's system setting.
- **International:** Names and text in any language and script are shown, entered, searched, and sorted as well as English is: no screen assumes Latin letters, a given name first, or one name per person, and text is never cut so a character breaks. Search ignores letter case and accents, such as é or ё, but not marks that make another letter in other scripts, such as Japanese が, though Cyrillic letters such as й also match their plain letter. Sorting, dates, and counts follow each person's own language settings, and scripts the typeface lacks fall back to the system's fonts. The [seed data](development-setup.md#fictional-seed-data) includes names in other scripts, so every screen is tried with them.

## Layout

- **Frame:** A deep-water sidebar on the left, the same in both modes, groups pages into sections. The sidebar shows only the pages the user's roles allow, including pages still to come, marked "Later", so people can see what Fathom will offer them. Fathom opens on the Overview, or, for a user who may not see the plan, on the first page their roles allow, or Help's Roles page if there is none. Help is the last section, open to everyone, with its own icon for each page. A top bar names where the user is and holds their account menu, wide enough for their email address, with Change password and Sign out.
- **Collapsed sidebar:** The sidebar collapses to a rail of icons, each naming its page on hover or focus, and remembers the choice.
- **Narrow screens:** The sidebar opens from a menu button, and closes when the user moves to another page.
- **Pages:** Each page starts with a heading and the page's main action on the right. Content sits in bordered panels on a canvas a shade darker than them.
- **History pages:** Change history and Access history, in the sidebar's History section, look alike: a search field, like a table's, then one row for each entry, newest first, with its date, year, and time, naming who did what in a sentence, with details dimmed after a colon, and a yellow dot, read aloud as "Worth checking", before entries that deserve a second look. The change history has a sentence for each record a save changed, such as "changed the list Sites: Name from Sites to Locations", where the field is in semibold and each value is set apart on a light ground, as a value is in code, as wherever a change is described, in a record's menu or on the Drafts page; records of a kind added or deleted together share one, such as "added 150 people", naming ten, with Show all for the rest. A save that changed several records lists five, with Show more for the rest. Show more at the end of the page reads older entries. The change history's search looks on the server in who made each change and the names and values involved, reading back through up to 2,000 saves at a time, with Show more to read on, and shows what matches first in each entry; the access history's searches the latest entries it shows.
- **Roles help:** Help's Roles page names each role beside what it lets a user do, with the user's own roles marked "Yours", followed by what each sensitivity covers. Wherever roles are chosen, each role shows the same description under its name.
- **Drafts help:** Help's Drafts page names each mark a person, list, or choice with a draft can show, drawn as on the People table and the Lists page, beside what it means, followed by what happens to a draft once saved, approved, rejected, or discarded, and what each choice in the Draft menu shows.
- **Sign-in and problem pages:** Only Fathom's name and mark above the form or message, with no other words.

## Type and Colour

- **Typeface:** IBM Plex Sans, at weights 400 for text, 500 for emphasis, and 600 for headings and names. Weight 700 is bundled for Mantine's own bold text, such as table headings.
- **Figures:** Dates, times, and numbers that line up in columns use figures of equal width.
- **Colours:** Defined once in the theme as CSS variables and used by name, never written into a page.

## Components

- **Tables:** Lists of records are tables in a panel, using the full width, each text cell on one line and cut short when it does not fit. Every table's column headers look alike: small, semibold, and dimmed, on one line of a set height, and its header row stays in view while its rows scroll. A page of a long table, such as People or Accounts, fills the window, and the table scrolls within it. A row's actions are in a menu behind a "⋯" button at its end, always shown. What a table's rows hold sets how tall they are: People's are dense for editing, and Accounts' show each person's initials, name, and email address. Rows show no audit detail, such as who changed a record or when; any date shown includes its year.
- **Records in a side panel:** Clicking a row opens its record in a panel sliding in from the right, at its own address, beside the table, which stays usable. Esc, the close button, or a click on the page outside closes it.
- **Entering data:** Where items are added or changed in a list, they are edited in place, from the keyboard: an empty row at the end takes new items, Tab moves between fields, Enter saves and starts the next, Esc cancels, and arrow keys move between items. Pasting several lines adds one item for each. Problems show on the row being edited.
- **Editing like a spreadsheet:** Tables where many records are entered, such as People, work like a spreadsheet. Arrow keys, Home, End, and Tab move between cells, Tab on to the next row at the end of one, and Ctrl+Home and Ctrl+End go to the first and last cells; Enter, F2, or typing edits a cell; Enter saves and moves down, Tab saves and moves across, Esc cancels, and Delete clears. Empty rows at the end take new records, which the page's main action, such as New person, goes to: Tab goes straight on to typing in the next cell, and Enter adds the record. A row being filled in is tinted as the draft it will be and marked "New, not saved yet" after an open dot, naming any required column still empty, such as "Site needed". An added record shows at once, as a draft adding it, and cannot be changed until it is saved. Pasting rows copied from a spreadsheet adds one record for each. A column drawing on a list is edited by typing to narrow its choices, which drop down below the cell, and picking one. Each column is as wide as what it can hold, up to about 30 characters: a column drawing on a list fits its longest choice, so a cell holding several is cut short, a date column fits the longest date, and a text column the longest value it held when the page opened. The first column has room for a draft's mark. No width follows what is typed, so editing never moves the table. Every column can be dragged by its header, or moved with Alt and the arrow keys or from its menu.
- **Searching, filtering, and sorting:** A search field above a table finds rows with every word typed anywhere in them, ignoring letter case and accents; Cmd+F on a Mac, or Ctrl+F elsewhere, goes to it from anywhere but a dialog, and Esc clears it, then goes back to the table. Each column's menu, open to viewers too, sorts by it, A to Z, by date, or in its list's order, adding it as the next level of the sort, or changing its direction in place when it is sorted already. It also opens the column's filter beside the header: text a value contains, dates from and to, typed as 2026-10-31, or choices to show, with retired ones under their own heading, each with an option for empty values. Sorted and filtered columns are marked in their headers. Above the table, each level of the sort is named in a pill, such as "Level ↑", in order, and so is each filter, each pill removing what it names, beside how many rows there are, such as "150 people", or, while rows are hidden, how many are shown, such as "35 of 150", with Clear all, which also clears the sort. Rows keep their place while they are edited, until the view next changes, and when nothing matches, the table says so.
- **Saved views:** A Views menu after the search field lists the table's saved views by name, the applied one checked, and applies the one chosen. It is named after the saved view applied, with a dot once the view has changed since, and offers Clear view, like Clear all, Save view…, which asks for a name in a dialog, and, for views the user may change, Update with the view as it is now, Rename…, and Delete view, which offers Undo. It is left out while there are no saved views and nothing to save.
- **Ordering:** Where people set an order, rows have a grip for dragging on wide screens, shown on hover or focus, and Alt with the arrow keys moves the selected row. Each row's menu offers the same moves and shows each action's shortcut.
- **Retiring:** Records that others use are [retired](../product/domain.md#table-terms) rather than deleted. Retired records are shown only when asked for.
- **Monthly resource grid:** The grid in the [Decisions Log](../product/decisions.md#planning) keeps people's names fixed on the left while months scroll sideways. Cycle and release ends are thin vertical lines labelled with their names, and each cell lists that month's work.
- **Dialogs:** Creating and changing settings, such as a list's name, happens in dialogs, which cannot be closed while a change is being saved.
- **Drafts:** How drafts look, and what can be done with them, on every table that has them.
  - **Marks:** A record with a draft is tinted light blue and marked after a dot: Draft, Draft: added, Draft: removed, Draft: moved, Draft: reordered, Draft: retired, or Draft: restored, with a yellow dot, or Rejected, with a red one. A record a draft removes is struck through and cannot be changed. Each tint has a darker version in the dark scheme, so text on it stays readable.
  - **Rows:** On People, each cell a draft changes is yellow, or soft red once rejected. Under the draft row is the person's live row, light green, dimmed, and marked Live: read only, skipped when moving between cells, and with each changed cell's live value read aloud.
  - **Columns:** A column with a draft is marked under its name, so the mark does not widen it, and a changed column has its live copy beside it, marked Live. A new column order shows the columns in their new places, each moved column marked Draft: moved, unless it is removed.
  - **Lists:** A list's row is marked Draft while anything in it waits, Draft: reordered when only its order does, and Rejected only once everything drafted in it was rejected. A choice drafted to be removed is struck through in the row and not counted. In the panel, each choice with a draft is tinted and marked, with its live row under it, and a moved choice is marked Draft: moved, with its old place dimmed and marked Live. A list or choice drafted to be retired or restored stays where it is until approved. The rows are not a spreadsheet's, so no single cell is tinted.
  - **Menus:** A record's menu starts with its name, then a divider. Its draft section starts with the draft's mark and any rejection's reason, then one line for each change, naming the field in semibold and setting each value apart, as in code, with who made the change. A list's menu has a short section for its own draft and one for a new order of its choices, each with its mark, who made it, and any reason. A click anywhere in a menu but its items closes it.
  - **Actions:** Those who may edit discard a draft, or resubmit a rejected one; a new order is discarded with Discard new order. Approvers approve or reject a waiting draft from its menu. A rejected draft offers Approvers nothing to decide until it is resubmitted, and a draft that depends on a rejected draft has Approve disabled, with "Waiting for a rejected draft to be resubmitted" under it. A moved column whose own draft waits, while the new order also waits, has one Approve… and one Reject… that decide both, and the dialog names both.
  - **Deciding several:** The Draft menu offers Approve N drafts… and Reject N drafts… for the waiting drafts shown, under a Waiting drafts label that, when a search, a filter, or Drafts applied hides some, says how many are shown, such as 9 of 11 waiting drafts shown. The dialog says how many related drafts it includes, and how many drafts it skips because they depend on a rejected draft.
  - **Draft menu:** The Draft button above the table, marked while its choices are not the defaults, filters to records whose drafts are waiting or rejected, or that have no draft, shown in a pill such as "Draft: Waiting", and chooses what to show: Drafts beside live, the default; Drafts applied, everything as it will be once the waiting drafts are approved, without live rows or removed records, and with rejected drafts taken back, so the Rejected filter is unavailable; and Live only, everything as it is now, read only, with the filter unavailable. Both choices are kept in the page address and in saved views.
  - **Drafts page:** Every draft as a sentence with what it changes, with a search. Approvers select waiting drafts there to approve or reject; a rejected draft, or one that depends on it, cannot be selected.
- **Undo, not confirmation:** Changes save at once, without asking for confirmation, except approving and rejecting drafts, which cannot be undone and so ask first, and the latest can be undone with Cmd+Z or Ctrl+Z. Changes seen in place, such as an added or moved item, show no notification. Changes that take something out of view, such as retiring or removing it, show a notification at the top right offering Undo, which closes after a few seconds or when a newer change is made. Failures stay until closed.
- **Empty and failed states:** An empty table says so in a few words. A table that cannot be loaded says so and offers Try again.
- **Messages:** Problems are shown in plain words saying what to do next, never as raw errors.
- **Styles:** Mantine's components, theme, and style props, such as a one-off size or margin, come first. Anything more goes in a CSS Module, never in a `style` attribute.
